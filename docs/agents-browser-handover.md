# Personal agent browser handover

## Status and scope

Personal agent browser handover is implemented for a running personal agent chat.
The agent opens its server-side browser through the existing `browse_page` tool
and can request that its owner take control. AIplane pauses that exact turn,
shows the owner a private browser panel in the chat, and resumes the agent after
the owner returns control.

The browser profile is agent-owned and persists in the configured runner work
root across browser container recreation. It is separate from the owner's local
browser and from every other agent. Persistent workspace availability is limited
to the verified local rootful Linux gVisor deployment; see
[`agents-workspace.md`](agents-workspace.md#operator-implications). This flow does
not promise that a live page or an in-progress challenge survives runner
restarts.

Organization agent handover, desktop access, file dialogs, downloads/uploads,
clipboard synchronization, arbitrary JavaScript, browser cookie inspection,
and sharing the live view with another person are not implemented.

## Owner flow

The agent must already have opened its browser in the current turn. It invokes
`browse_page` with the `handover` action. The normal agent tool selection and
action rules still gate that call. AIplane creates a durable
`BrowserHandover` suspension with a 15-minute timeout and deny fallback, then
puts the exact browser lease into human-control mode.

The owner claims control in the same chat session. The panel shows a live
viewport, accepts click, key, editable-form text and scroll input, and offers
explicit **Return to agent** and **Stop run** actions. Input extends the five
minute idle deadline, up to the 15-minute maximum. Merely polling frames does
not renew the deadline. The runner admits only one controller and fences agent
browser commands for the duration of the handover.

Returning control reserves the existing chat worker before claiming the
suspension. The runner clears non-hidden form values and browser observation
markers and console buffers, then restores the lease for the resumed turn. The
Agent must inspect the page again; the handover tool returns no frame, DOM, or
typed secret. Stopping cancels the waiting personal agent run.

The controller ID is generated by the browser client and remains stable across
one automatic retry. The runner treats a repeat claim from that same ID as
idempotent, which handles a lost HTTP response. A different controller remains
rejected while the lease is claimed.

## API and trust boundary

The web client uses these authenticated, same-origin, no-store endpoints:

| Endpoint | Operation |
|---|---|
| `POST /api/v0/chat/sessions/{session}/turns/{turn}/browser-handover/{request}/claim` | Claim the one owner controller using a client-generated opaque controller ID. |
| `POST /api/v0/chat/sessions/{session}/turns/{turn}/browser-handover/{request}/frame` | Get one volatile JPEG viewport frame. |
| `POST /api/v0/chat/sessions/{session}/turns/{turn}/browser-handover/{request}/input` | Send one typed, sequenced click, key, text or scroll input. |
| `POST /api/v0/chat/sessions/{session}/turns/{turn}/browser-handover/{request}/finish` | Fence human input and return control to the agent. |
| `POST /api/v0/chat/sessions/{session}/turns/{turn}/browser-handover/{request}/abort` | Cancel the waiting personal agent run. |

Every request checks the signed-in owner, same-origin request, personal agent
association, session, turn, suspension, runner lease and handover generation.
The runner remains authoritative for exclusive control. Browser frames are
returned only to the current controller; they are not written to chat events,
attachments or model input. Input and frame requests use JSON bodies and are
size capped. Input sequence numbers must increase; gaps are allowed so a lost
response does not permanently wedge control.

This does not make a malicious page safe. A user can see credentials that the
page visibly renders, and a page can echo submitted values outside ordinary
form fields. The handback cleanup reduces accidental replay to the model but
cannot guarantee removal of secrets from arbitrary page content or pixels.
Owners should use a supported login flow and return control once complete.

## Reused mechanisms

The feature extends the existing `browse_page` browser process, agent-scoped
sandbox lease, runner admission and lifecycle, durable chat suspension, worker
reservation, authenticated `/api/v0` session, and current chat UI. It adds no
second scheduler, approval system, model selector, browser service, or external
runtime dependency. The typed control protocol is in `shared::sandbox`; the
runner owns the mode fence and deadlines; the API resolves the authenticated
Agent/session/turn binding; and the existing chat worker resumes the same turn.

## Verification

Runner tests cover idle and maximum deadlines, execution fencing, stale input,
same-controller claim retry, and rejection of a competing controller. API
tests cover same-origin enforcement and private response headers. The
`openapi_drift` suite verifies all five routes and their request/response
schemas. The web component is exercised through the existing chat suspension
rendering and localization checks.

Manual Chrome walkthrough remains necessary to verify the live panel against a
real authenticated development session. A runner restart invalidates transient
control handles; the waiting turn can then fail closed and require a new
browser session. A shared persistent work root across independent runner
replicas is unsupported.
